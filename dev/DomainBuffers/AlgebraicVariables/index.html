Algebraic variables

Experimental

The support for algebraic variables is experimental. The functions described on this page are not yet part of the public API, and may change without being considered a breaking change.

Ferrite's algebraic variables (AlgebraicVariable) are global unknowns that are not associated with the grid, for example a Lagrange multiplier that enforces the mean value of a field, a cavity pressure, or the load factor in a path-following method. Their degrees of freedom are not part of celldofs. To use them in the element or facet routines, they are given to the DomainSpec for the domains that use them,

dh = DofHandler(grid)
add!(dh, :u, ip)
add!(dh, :λ, AlgebraicVariable())
close!(dh)
domain = DomainSpec(dh, material, cellvalues; algebraic_variables = (:λ,))

The same keyword is used for facet domains, and the same variable can be used in several domains, including both cell and facet domains. The contributions from the different domains are then added during assembly. See Mean value constraints for a complete example.

Each element in algebraic_variables is either the name of a standalone variable, as above, or an AttachAlgebraic declaration of a variable attached to a field, see Attached variables.

Local degrees of freedom

For each item (cell or facet) in a domain with standalone algebraic variables, the degrees of freedom of each standalone variable are added after the degrees of freedom of all fields (including those of attached variables), in the given order. Consequently, the following have the size of, and are ordered according to, these local degrees of freedom:

  • ae and get_aeold(buffer), including the current and old values of the algebraic variables
  • re and Ke, including the contributions to the equations for the algebraic variables
  • celldofs(buffer), including the global degrees of freedom of the algebraic variables

Standalone variables don't change the local dof range of the fields, and dof_range(buffer, name) also gives the range for an algebraic variable with name name. Since ae contains more values than the number of shape functions, the element routine must pass the dof range when evaluating a field, e.g. function_value(cellvalues, q_point, ae, dof_range(buffer, :u)). The value of an algebraic variable is obtained as

av = FerriteAssembly.get_algebraic_values(buffer, :λ)
λ = algebraic_value(av, ae, dof_range(buffer, :λ))

which, e.g., gives a tensor for an AlgebraicVariable{SymmetricTensor{2, 3}}. Ferrite.getfieldnames(buffer) and the dofrange given to create_cell_state contain the fields, followed by the standalone algebraic variables. Attached variables are not included, see Attached variables.

FerriteAssembly.get_algebraic_values — Function
get_algebraic_values(itembuffer::AbstractItemBuffer, name::Symbol)

Get the Ferrite.AlgebraicValues for the algebraic variable name, which must be one of the standalone variables given as algebraic_variables to the DomainSpec. Together with dof_range(itembuffer, name), the value of the variable is then algebraic_value(get_algebraic_values(itembuffer, name), ae, dof_range(itembuffer, name)).

Sparsity pattern

The entries for the algebraic variables are not included in the default sparsity pattern. The required coupling information for the domains is created by

FerriteAssembly.algebraic_couplings — Function
algebraic_couplings(buffers...)

Create a Vector of coupling descriptors for the domains with algebraic variables (see the algebraic_variables keyword of DomainSpec) in buffers. Each element in buffers can be a domain buffer, a DomainBuffers, or a Simulation. The output can be passed to Ferrite's allocate_matrix, to allocate the entries required for the algebraic variables in the sparsity pattern, i.e.

algebraic_couplings = FerriteAssembly.algebraic_couplings(cellbuffers, facetbuffers)
K = allocate_matrix(dh, ch; algebraic_couplings)

For each domain, all fields in the domain are coupled to all algebraic variables in the domain, and all algebraic variables in the domain are coupled to each other. If this gives too many entries in the sparsity pattern, the coupling descriptors can instead be created manually. If more coupling entries are desired, they can be push!ed to algebraic_couplings.

source

Ferrite's allocate_matrix also accounts for constraints, e.g. affine constraints where the degrees of freedom of an algebraic variable are the masters. Constraining the degrees of freedom of algebraic variables is done with AffineConstraints, and these can be applied both locally (with a ConstraintHandler given to the KeReAssembler) and to the global system after assembly. A degree of freedom that doesn't get any contributions, e.g. a component of a tensorial variable that isn't used in any element, must be constrained to avoid a singular system matrix.

Multithreading

Multithreaded assembly of domains with algebraic variables requires an atomic assembler, e.g. KeReAssembler(K, r; atomic = true). Otherwise, such domains are assembled sequentially.

Attached variables

An algebraic variable can also be attached to a field. The degrees of freedom of the variable then act as additional degrees of freedom of the field, which is useful when the field contains a global contribution, for example

  • the constant out-of-plane strain, $\varepsilon_{33}$, in generalized plane strain, see Generalized plane stress;
  • the macroscopic displacement gradient, $\boldsymbol{H}$, in computational homogenization with $\boldsymbol{u} = \boldsymbol{H}\cdot[\boldsymbol{x} - \boldsymbol{x}_\mathrm{c}] + \tilde{\boldsymbol{u}}$;
  • rigid body modes or global enrichment modes.

The attachment is declared with

FerriteAssembly.AttachAlgebraic — Type
AttachAlgebraic(name::Symbol => field::Symbol; indices = nothing)

Experimental. Declaration, given in the algebraic_variables keyword of DomainSpec, that the degrees of freedom of the algebraic variable name are attached to the spatial field field. For each item (cell or facet) in the domain, these dofs are then placed directly after the dofs of field, and are included in dof_range(buffer, field). The values object of field must therefore provide one shape function for each attached dof, after the field's ordinary shape functions, see Attached variables. The attached variable is only seen through field, i.e. name is not available in the item buffer (e.g. for dof_range and get_algebraic_values), nor in the dofrange given to create_cell_state.

The attached components are given as indices, in the order of the attached shape functions. indices can only be omitted if the variable has a single component, e.g. a scalar. Each index is an Int for scalar and Vec variables, and a tuple, e.g. (3, 3), for tensorial variables. For symmetric tensors, (i, j) and (j, i) refer to the same component. Components that are not attached in any domain don't get any contributions, and must be constrained.

Several variables can be attached to the same field, but each variable can only be given once per domain, i.e. either attached to one field or as a standalone variable. The attached variables of a domain are given by attached_variables.

source

for example,

dh = DofHandler(grid)
add!(dh, :u, ip^2)
add!(dh, :p, ip)
add!(dh, :H, AlgebraicVariable{Tensor{2, 2}}())
add!(dh, :λ, AlgebraicVariable())
close!(dh)
domain = DomainSpec(dh, material, (u = cellvalues_u, p = cellvalues_p);
    algebraic_variables = (FerriteAssembly.AttachAlgebraic(:H => :u; indices = ((1, 2), (2, 1))), :λ))

For each field, in the order of their degrees of freedom in celldofs, the local degrees of freedom are the field's degrees of freedom, followed by those of the variables attached to the field, in declaration order. Then the standalone variables follow. In the example above, with linear quadrilaterals, the local dof ranges are u = 1:10, p = 11:14, and λ = 15:15, where the two components of H are the dofs 9 and 10. Hence, dof_range(buffer, :u) includes the attached degrees of freedom, such that the values for :u (cellvalues_u) must provide 10 base functions, where the last two correspond to the attached components of H. The attached variable is only seen through the extended field: H is not available in the buffer, e.g. for dof_range and get_algebraic_values, nor in the dofrange given to create_cell_state. An attached variable therefore doesn't change the element routine: the field just has more degrees of freedom, and the values for the field must provide the additional base functions. This is checked when setting up the domain. An existing element routine can thus be used unchanged, as long as the domain has no standalone variables, see Attached and standalone variables in the same domain.

The attached variables of a domain, with their fields and components, are given by

FerriteAssembly.attached_variables — Function
FerriteAssembly.attached_variables(db::AbstractDomainBuffer)
FerriteAssembly.attached_variables(dbs::FerriteAssembly.DomainBuffers, domain::String)
FerriteAssembly.attached_variables(sim::Simulation[, domain::String])

Experimental. Get the algebraic variables that are attached to fields in the domain represented by db or dbs[domain], see AttachAlgebraic. This is a NamedTuple with an entry name = (field = field, components = components) for each attached variable, in the order of their local degrees of freedom. components are the attached components as indices into algebraic_dofs(dh, name), in the order of the attached base functions, such that algebraic_dofs(dh, name)[collect(components)] are the attached global degrees of freedom. The NamedTuple is empty if no variables are attached to fields in the domain.

source

For the example above, FerriteAssembly.attached_variables(db) gives (H = (field = :u, components = (3, 2)),), where db is the domain buffer created with setup_domainbuffer(domain).

Note that the LoadHandler only adds contributions to the field's own degrees of freedom. If an external load does work on the attached base functions, this must be included in the element routine, or added to the global residual at algebraic_dofs(dh, name).

Values for attached variables

FerriteAssembly does not provide values types with additional base functions; these are problem specific. A custom values type for a cell domain should subtype Ferrite.AbstractCellValues and define

  • getnbasefunctions, including the attached base functions;
  • getnquadpoints and getdetJdV;
  • shape_value and shape_gradient for all base functions. These must return the same type for all base functions, and should not allocate. The value and the gradient are independent, i.e. the gradient of an attached base function need not be the gradient of its value (e.g. a zero value with a non-zero out-of-plane gradient);
  • getngeobasefunctions and geometric_value (or spatial_coordinate);
  • reinit!(values, cell::Union{Nothing, Ferrite.AbstractCell}, x::AbstractVector{<:Vec}), where data depending on the cell can be updated (e.g. the position of the quadrature points). deepcopy must give an independent copy, as used for multithreading;
  • optionally shape_hessian, if used by the element routine.

Ferrite's generic methods then give the remaining accessors, e.g. shape_symmetric_gradient, shape_divergence, function_value, and function_gradient. For a facet domain, the values type should subtype Ferrite.AbstractFacetValues and define reinit!(values, cell, x, facetnr) instead. A custom cell values type can be checked with

FerriteAssembly.check_values_interface — Function
FerriteAssembly.check_values_interface(values::AbstractCellValues, cell, x; hessians = false)

Experimental. Check that the cell values type of values supports the accessors that element routines typically use, see Values for attached variables. This is intended for testing custom values types, e.g. for fields with attached algebraic variables (see AttachAlgebraic). values are first reinitialized with reinit!(values, cell, x). Then, for all quadrature points and all base functions, it is checked that

  • shape_value, shape_gradient, and their derived accessors (shape_symmetric_gradient, shape_divergence, and shape_curl for vector-valued functions) can be called, and return the same type for all base functions;
  • the corresponding function_* accessors can be called for local dof values ae, and for ae with a dof_range;
  • getdetJdV and spatial_coordinate(values, q_point, x) can be called;
  • none of these allocate.

If hessians = true, shape_hessian and function_hessian are included as well. Only cell values are supported; custom facet values cannot be checked with this function.

Returns true if all checks pass, and throws an error describing the first failure otherwise.

source

If the values type lifts a problem to a higher dimension, e.g. to use a 3d element routine for a 2d grid, the coordinates given to the element routine can be lifted as well, by overloading

FerriteAssembly.routine_coordinates — Function
FerriteAssembly.routine_coordinates(values, x)

Experimental. Return the cell coordinates given to the element (or facet) routines and to create_cell_state, via getcoordinates(buffer), for the grid's coordinates x and the values object values (as given to DomainSpec). Defaults to x, but can be overloaded for a values type, e.g. to give 3d coordinates for values that lift a 2d problem to a 3d element routine, see Values for attached variables. This function is called after reinit!(values, cell, x), and should not allocate. A typical implementation therefore returns coordinates stored in the values object, which are updated in reinit!.

source

Attached and standalone variables in the same domain

A standalone variable is an additional entry in the local degrees of freedom, placed after all fields (including their attached degrees of freedom). The element routine must therefore use dof_range(buffer, name) for each field and each standalone variable, as for any multi-field problem. In the example above, the routine evaluates :u (including the attached components of H) with dof_range(buffer, :u), :p with dof_range(buffer, :p), and gets the value of :λ with dof_range(buffer, :λ), see Local degrees of freedom.

Further details

  • Automatic differentiation: Defining only element_residual! works as for other cell domains, and the stiffness then includes the coupling to the algebraic variables. There is no automatic differentiation for facet domains.
  • Renumbering: The global degrees of freedom of the algebraic variables are updated once when starting to work a domain, such that renumbering the dofhandler after setting up the domain buffer is supported.
  • Residual scaling: ElementResidualScaling calculates one factor for each algebraic variable, in addition to the factor for each field. The factor for a field only includes the field's own degrees of freedom, and the factor for an attached variable includes its attached components.
  • Workers evaluating fields: The SimpleIntegrator and QuadPointEvaluator pass the values and gradients of the fields, including the contributions from attached variables. The values of the standalone algebraic variables are not passed.
  • Loads: The contributions added by the LoadHandler cannot depend on algebraic variables. Such contributions can be implemented with facet_routine! or element_routine!.
  • Coupled simulations: A coupled buffer, see get_coupled_buffer, gives access to the algebraic variables of the coupled simulation in the same way as for the buffer itself.
